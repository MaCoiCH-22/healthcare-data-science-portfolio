The question

When a data feed contains a bad identifier or an invalid reference, which entries can still be used? The engine makes those decisions visible for data engineering and clinical informatics teams.

Trace the source of a failure

Start with direct failures to find records that need correction. Downstream entries can then be checked against the repaired references.

Methods and implementation
  1. Synthetic FHIR R4 bundles
  2. Structure and rule checks
  3. Dependency quarantine
  4. SQLite lineage
  5. Quality report

The pipeline checks selected Patient, Encounter, and Observation fields and references. It stores batch and entry identifiers, records findings, and exports aggregates. The local policy includes a limited laboratory terminology set and measurement checks.

Limitations

All feeds are generated fixtures. Rules cover a deliberately bounded subset of R4 and local policy. Real feeds may require profile validation, a terminology service, external-reference resolution, and privacy and governance review.

What I’d check next

A feed owner could use the counts to trace a cluster of failed entries to its upstream cause. For wider deployment, run the rules alongside a full profile validator and test error handling against more representative integrations.

Sources and reproduction

The project bundle includes the deterministic fixture generator, validation pipeline, SQLite schema, and tests.
